## 用語の定義

- 系 = 入力 → 関数 → 出力（参照: https://zenn.dev/kisaburo_y/articles/9e2fcefa88ec91）
- 二次情報: 消したら再生成できる情報。保存するのは計算量のキャッシュにすぎない。
- 一次情報: 消したら再生成できない情報。次の2つに分かれる。
  - 可変の一次情報: 書き換えられるもの（関数・設定・系外の関数へのポインター）。git で管理する。
  - 不変の一次情報: 書いたら変わらないもの（ログ・生データ・受信メール・受け渡し箱の中身）。ストレージに置く。
- 機密情報: 次のどちらか。
  - credential: .env に格納するとユーザーが決めた情報。
  - 他人の情報: 法または契約により公開が禁じられている情報。判定は中身でなく出所で行い、オフィス（業務）・imc（受信メール）由来のものはこれとみなす。
- "_" で始まるファイル: git の管理外（二次情報、または不変の一次情報）。

## 大前提0 - 開発とは何か

- 開発は以下を決めることから始まる
  - 目的: 誰(クライアント)のために何をするのか
  - 入力: SSoT(1次データ)は何か
  - 交換形式：サブシステム間のデータ交換形式
  - 出力：クライアントの入力SSoT

## 大前提1 - SSoT は実装

従来の常識: 文書（設計書）がSSoT、実装はその帰結。  
今後の常識: 実装がSSoT、文書は実装から自動的に作成される二次情報。自動生成を成立させるために、実装が処理のモデルをダイレクトに表現しなければならない。  
実装 = ディレクトリ階層構造、ディレクトリ名、ファイル名、ファイルの内容  
ファイル = コード、データ、設定、ツール、文書

## 大前提2 - 実装はリポジトリに含めよ

機密情報、二次情報、不変の一次情報を除き、コード・設定・データ・ツール・文書は原則としてファイル化しリポジトリに含める。  
「DBが大きすぎてリポジトリに入らない」のではない。  
多くの場合、SSoTと二次情報を同じデータベースに混在させていることがDBが巨大化する原因である。  
それを防ぐことで、「リポジトリを clone すれば、AIも人間も同じシステムを理解・再現・変更できる」状態を目指す。

## 大前提3 - 設計検証哲学：収束性中心主義（DJC）

### 基本思想
「判定するな。収束を見よ。（Don't judge. Converge.）」
「裁くな。比べよ。（Don't judge. Compare.）」

KPIやテストケースによる評価は、事前に想定された評価軸に依存する。  
複雑なシステムで問題となるのは、しばしば評価そのものである。

### 評価関数の限界
KPI は現実 R の低次元射影 K = f(R) であり、情報落ちが避けられない。  
指標が目標になると良い指標でなくなる（Goodhart の法則）。

### DJC の原則
同一目的を独立に実装した A(x) と B(x) を比較する。

- A(x) = B(x) → 暫定採用
- A(x) ≠ B(x) → 人間が差分のみを調査

正解を事前定義しない。独立な探索過程の収束を観測する。

従来のテスト：「想定内」を増やそうとするテスト  
回帰テスト：「想定外」を検知するテスト

### 独立性の最大化
実装者・言語を変えるだけでは不十分。  
**異なる計算モデル**（例：状態遷移マシン vs 純粋関数 vs 述語論理）で実装することで
故障モードが異なり、共通の誤りを減らせる。

### コスト再配分
実装コストは増えるが、レビュー・評価・承認の認知コストが大幅に下がる。  
人間が扱う対象はシステム全体ではなく差分集合のみ。

品質保証の本質的コストは「コードが正しいと信じるための認知コスト」であり、
DJC はこれを機械的な収束判定に置き換える。

## 大前提4 - 設計案は過程ごと示す

issue や PR で設計案を示すときは、
結論と証拠だけでなく、結論に至る過程を
次の 3 層で示す。

1. 結論と、読む人に決めてほしいこと
   最初の数行。急ぐ人はここで終われる。
2. 編集した問答
   判断が動いた箇所だけを「問い → 答え → 決定」で。
   発言は要約せず引用する。捨てた案も残す。
   AI が抜粋したら、決定はヒトが確かめる。
3. 生の記録へのリンク
   疑問が出たときに辿れるように。
   認証情報が混ざらないことは道具で機械的に検査する
   (読む人はアクセス権を持つので、
   患者情報・機密の確認は要らない)。

理由: 結論だけでは捨てた案と前提が覆った瞬間が
消え、読む人が考え直すか質問することになる。

## 小前提

- 開発対象も開発環境もWindowsではなくLinux VM上に構築
  - LOCAL は WSL 上のコンテナ
  - ALPHA, BETA, PROD は可能ならば Azure 上の Linux VM。不可能ならばコンテナ
  - 操作方法はできる限り統一。例: コピーは rsync
  - Windows固有のツールは極力避ける。例: PowerShell
- 設計思想
  - 物理モノリス・論理マイクロ
  - コード、データ、設定(機密情報を除く)、説明、ツールをすべて git で履歴管理
  - ただしデータは可変の一次情報に限る。それ以外のデータはファイル名の先頭に "_" を付与し、.gitignore で無視する。
  - 文書ファイルのうち、エージェントへの指示を書いてあるものは1次ファイルなので、プロンプトで明示されない限り編集禁止。
  - 共通化「できる」ものを共通化するな。共通化「せざるを得ない」ものを共通化せよ。
    - 空間軸だけでなく時間軸にも適用する（時間軸上の共通化）。
      「今」と「未来」が同じものを共有するのも共通化である
      （「いつか使うかも」で残すデータ、期限のない鍵、常設の権限、将来を見越した抽象化）。
    - ∴「共有せざるを得ない場所で、共有せざるを得ない間だけ共有せよ」
    - 時間方向の共有は「消していない」という不作為から生まれるので見えにくい
  - 冪等性確保。
  - あるリポジトリを実際に使用するために必要な初期化処理をひとつのコマンドにまとめる。
    例：initialize.sh
- GUI ツールは開発環境の末端の部品。GUIで作業フローを作ってはならない
  - 作業フロー（手順の連なり）は常にCLIスクリプトとして組む。GUIはそのフローの末端、人間が見る／入力する接点としてのみ存在してよい
  - したがってGUI ツールは、AI Agent自身が操作する手段としては禁止。人間向けインターフェースとしての使用は可
    例: `chrome.sh` でブラウザ画面を開き人間に見せる／操作させるのは可。AI Agentがブラウザを自動操作する（クリック等）のは不可
- 階層化入力モデル: 複数ステップの人間入力が必要な対話UI（CUIのポップアップメニュー、GUIのモーダルダイアログの重ね表示、等）は、媒体を問わず「フレームのスタック」として設計する
  - フレームは「選択（リストから選ぶ）」か「入力（自由テキスト）」のいずれか
  - 確定した値が終端（適用可能な値）なら、スタックを全部畳んで呼び出し元へ戻る
  - キャンセル操作（Escape・戻るボタン等）は常にスタックを1段だけpopする（最上位でのキャンセルのみ全体キャンセルになる）
  - 「その他」等の選択肢が、選択フレームから入力フレームへの遷移トリガーになる
  - 実例: bin/worklog/tools/worklog_editor.py（Ctrl+E起点の属性変更、CUIポップアップの3階層）
- 非同期処理モデル（人間を待つ）: 複数ステップの自動フローの途中に人間の判断・入力が要るとき、そこで処理を人間へ手渡して終える（ハンドオフ）のではなく、パイプライン側が人間の完了を wait して続きを実行する。人間は「パイプラインが待つ再利用可能な部品」であって終端ではない（AIも同格の非決定論的部品）
  - 人間の完了・中断・破棄を機械的に判別できる契約（exit code 等）を必ず設ける
  - 人間の入り口と出口を AI／スクリプトで挟んで検証する（入力を下流へ通す前に妥当性確認、人間の出力を検証してから下流へ渡す）。「副作用の直前に人間の許可を求める」も、この wait の一種
  - 実例: bin/worklog/tools/worklog_day_close.sh（worklog_editor.sh の exit code 0/1/2 を wait して Jira/freee 登録へ分岐。editor は保存時に lint で人間の編集結果を検証する）
- bash, python, その他を問わず
  - 引数の意味は位置で決まる
  - オプションは --dry-run, --confirm など限られたもののみ
  - default 値は原則無し
  - 入力は原則 stdin
  - 出力は原則 stdout
  - メッセージ・ログは stderr
  - 無引数で実行したり無効なオプションや誤った数の引数を与えるとstderrに使用法と機能の説明を表示
    - 使用法は
      ```
      command_basename: メッセージ(例: Too few arguments)
      usage: command_basename <env_name> <arg1> <arg2> ...
      example: command_basename LOCAL foo bar
      ```
    - 機能の説明は、bash スクリプトの 2 行目以降のコメント行の連続から取得
  - 失敗時にも成功時にも、「次に何をすべきか」を stderr に出す。
- 文書の言語・書式・内容の変換
  - 改行はできる限り保存する。例えば日本語マークダウン→英語マークダウン→レンダービューに於いて、もともとあった改行は原則として保存する
    - そのためにマークダウンの行末にアスキースペースを2個追加する
    - ただし、すでにある場合を除く
    - ただし、日本語版が commit 済みならその限りでない
  - 自然言語を含む文書(md)・画像ファイルは原則として日本語版と英語版を作成
    - 原本は日本語
    - 英語は日本語から翻訳
    - ただし、日本語版が commit 済みなら翻訳不要
    - ただし、1000 行を超える文書(md)ファイルは、その旨をユーザーに表示してスキップし、ユーザーの手動翻訳を待つ
    - 翻訳には ~/bin/translate.sh を使う
  - 個人情報・機密情報が無いことを確認する
    - あればユーザーに確認の上で一般的な表現や「ありえない」表現に置換する
      - 例: https://starship.jp/ => https://foobar.co.jp/
      - 例: 山田喜三郎 => 日本太郎
      - 例: takamitsu-ishioka => socrates-of-athens

```
cd ~/bin
ls -1
```

- を起点として
- 開発対象に関するすべての必要な知識を
- 芋づる式に引き出せる

ツールの体系を作りたい。

## スクリプト作成の規則

- WSL 上で動作する
- 設計は UNIX 哲学を採用: Do one thing and do it well.
  - スクリプトは部品。
  - 巨大（複雑）な部品は作らない。
  - 複雑な機能は単純な部品を組み合わせて実現する。
- AI は部品メーカー
  - ❌AI が毎度APIやCLIコマンドを呼ぶ
  - ⭕️AI はAPIやCLIコマンドをスクリプト化する
  - ⭕️ユーザーが自身で、またはAIがユーザーの指示で、スクリプトを組み合わせたスクリプト作る
  それにより
  - AIによる推論の揺らぎを小さくできる。
  - 推論コスト（時間・課金）を削減できる。
  - 成果をスクリプトとして資産化できる。
  - 人間もAIも、より高い抽象度の問題に集中できる。
  - 実行時の分担: 決定論的な手順として書けるものはスクリプトにする。書けない部分（翻訳・要約・判断）だけを小さく切って AI に渡す。例: ~/bin/translate.sh
  - 推論でしかできないか否かはユーザーが判断する。AI は提案だけを行い、決まるまではスクリプトとして扱う。
  - 検証と組み立て（比較・集計・結合）は AI ではなくスクリプトにやらせる。AI の出力を AI に判定させない（大前提3 DJC）。
- 複雑な処理
  - 実体は python
    - 単独実行をしない
    - 常に bash のラッパーから呼び出す
    - 実行許可を付けない
  - bash で薄いラッパー
  - つまり、foobar.py と foobar.sh を常にセットで作る
  - foobar.sh で引数をチェックし、python スクリプトを呼び出す
  - python スクリプトには実行許可を付けない。
  - bash ラッパー(.sh)には実行許可(+x)を付ける。もし新規/既存の .sh が実行許可
    無し(644)でgitに記録されていたら、単純な chmod 漏れとは限らず、リポジトリが
    元々Windowsファイルシステム(WSLの /mnt/c/ など)上にあった可能性を疑う —
    NTFSはunixの実行権限ビットを保持できないため、そこで commit すると意図せず
    644で記録される。疑わしい場合は該当リポジトリ全体を `git ls-files -s` などで
    一括チェックする。
  - 無引数実行時や不正な引数・オプションによる起動時は
    - エラーメッセージ
    - 使用法
    - 使用例
    を表示
  - 引数の意味は位置で決める
  - オプションは --dry-run, --confirm など限定的に
    - --dry-run: 新規作成、更新、削除を行わないモード
    - --confirm: 実際に新規作成、更新、削除を行うか否かとは無関係に、新規作成、更新、削除処理の直前にユーザーの許可を求めるモード
    - 入出力諸元の表示: --dry-run や --confirm の有無とは無関係に、副作用（新規作成、更新、削除）のあるスクリプトは実行前に入出力の諸元を一か所で分かりやすく明示する
  - 既定値は使わない
  - 機密情報
    - credential は .env や .env.<環境名> から読む
    - .env は .env.template からユーザーがコピーし、手動で書き換える
    - .env.<環境名> は .env.<環境名>.template からユーザーがコピーし、手動で書き換える
    - 環境名は LOCAL|ALPHA|BETA|PROD
    - 環境変数は使わず、.env から読む
    - .env や .env.<環境名> を書くのは常にユーザー
    - Coding Agent は .env を直接読まない
    - Coding Agent は .env.template や .env.<環境名>.template を読み書きする
    - sourceは拡張子なしのファイル名だと$PATHを先に探す — cd dir && source .envのように相対名で書くと、~/binが$PATHに含まれる環境では意図しない親ディレクトリの.env(今回は~/bin/.envのJIRA用)を拾う。source "$SCRIPT_DIR/.env"のようにスラッシュ付き絶対パスで書けば安全。
    - bash -xはシークレットを含む変数をトレース出力してしまう — .envを扱うデバッグでは-xやset -xを避ける。
    - freeeのwork_records(日次集計)とtime_clocks(打刻イベント一覧)は非同期でズレることがある — work_recordsのclock_in_atがnullでも、time_clocksには実際の打刻が記録済みということがある。打刻の実在確認はtime_clocks(生イベント)を信頼する。
    - freee WebGUIの「打刻」タイムライン画面はtime_clocks(生イベント)ベースで描画される。work_record_set.sh(PUT /work_records)でwork_recordsだけ更新しても、対応する打刻イベントは増えないため打刻タイムラインには反映されない(休憩・退勤の打刻イベント自体が無いまま)。ただし「勤怠」の日別詳細/集計画面はwork_recordsを正しく反映するので、そちらで確認すること。過去時刻の打刻イベントをtime_clocks側に追加する手段は無い(time_clock_punch.shは当日なら現在時刻でしかPOSTできない)。
    - OAuthのrefresh_tokenは「都度リフレッシュ」より「401でreactiveにリフレッシュ」が安全 — freeeのrefresh_tokenは1回使うと無効化(ローテーション)されるため、リフレッシュ回数を増やすほど「新トークン取得はできたが.env書き込み前に失敗して詰む」リスクが増える。401検知→自動リフレッシュ→1回だけ再試行、という形にスクリプト側で吸収するのが良い。
  - jq は使わない。jq が必要な時は python で書く
- 単純なものは直接 bash で書く
- 入出力
  - 形式
    - TSV または JSON。
    - 実行時の形式は引数 (tsv|json) で示す
  - 入力は原則 stdin 
  - 出力は原則 stdout
  - メッセージや進捗報告は stderr (言語は英語)
  - 時間のかかる処理は
    timestamp(JST) 31/971 メッセージ
    みたいな進捗報告
  - 木構造状の探索なら
    timestamp(JST) 31/971 > 4/80 > ... メッセージ
    みたいな進捗報告
- exit code
  - 正常終了 0

## システム整合性検査

- システムとは、コード・データ・設定・ツール・説明をノード、依存関係をエッヂとするグラフである
- 不整合とは、次の状態のどれかである
  - 存在不整合
    依存先／依存元ノードが存在しない
  - 内容不整合
    ノードは存在するが内容が矛盾している。
  - 関係不整合
    エッジの構造が期待と異なる。  
    例えば循環依存、禁止された依存、誤った向きなど。
  - 連結性不整合
    ノードまたは部分グラフが孤立している。  
    到達不能コード、誰にも使われない設定、CIから呼ばれないツールなど。
- システムの一部を変更すると連鎖的に不整合が発生し得る。  
  特にパス名やファイル名やディレクトリの階層構造を変更したときは、不整合の発生と波及を検査しなければならない。
