# home-ide-developer

[🇺🇸 English](README.md) | 🇯🇵 日本語

> **ホームディレクトリは、IDEである。**

これは設定ファイル集ではありません。

少なくとも、作者はそのつもりではありません。

`~/.bashrc`、`~/bin`、Git、Python、Claude Code、WSL、そして小さなシェルスクリプトたち。

普通なら「開発環境の周辺」と呼ばれるものを組み合わせて、**ホームディレクトリそのものを開発環境にしてしまおう**という試みです。

名前は **home-ide-developer**。

IDEをインストールするのではない。

**住んでいる場所をIDEにする。**

---

## なぜこんなものを作ったのか

昔、UNIXを触っていて気づいた人たちがいました。

UNIXには巨大な「開発環境」というものがない。

エディタがある。
シェルがある。
コンパイラがある。
`grep` がある。
`sed` がある。
`awk` がある。
Gitがある。

そして、それらをつなぐことができる。

```text
小さな道具
    |
    +-- 小さな道具
    |       |
    |       +-- 小さな道具
    |               |
    +---------------+
            |
          仕事
```

つまり、

> **UNIXそのものがIDEだった。**

ならば2026年、生成AI時代のIDEとは何だろう？

答えは案外、同じなのではないか。

---

## AIは「IDEの中にいる機能」ではない

このリポジトリでは、AIを特別扱いしません。

AIはコードを書くことができます。
調査できます。
設計できます。
テストできます。
ドキュメントも書けます。

しかし、それだけでは資産になりません。

毎回AIに、

> 「このファイルを読んで、こうして、次にあれをして……」

と説明していたら、人間がGUIを毎回クリックしているのと大差ありません。

そこで発想を逆転します。

**AIには部品を作らせる。**

一度うまくいった操作は、bashやPythonのコマンドにする。

```bash
$ something-useful input output
```

次からAIも人間も、それを使えばよい。

推論は揺らぐ。

**コマンドは揺らがない。**

AIが賢くなるほど、AIに毎回考えさせない仕組みの価値は上がります。

---

## `~/bin` は第二の脳である

何か面倒な作業をしたとします。

一回目は手でやる。

二回目も手でやったら、少し反省する。

三回目も手でやろうとしたら、

**スクリプトを書く。**

たとえば、

```bash
$ foo-fetch ...
$ foo-convert ...
$ foo-compare ...
```

という小さなコマンドを作る。

すると昨日の自分が考えたことを、今日の自分は考えなくてよくなります。

これは単なる「自動化」ではありません。

**思考のコンパイルです。**

人間の判断を、再実行可能な形に落とす。

そして、その成果を `~/bin` に置く。

だからこの環境では、ホームディレクトリが使い込まれるほど、本人より少しずつ賢くなっていきます。

本人が物忘れしても大丈夫です。

`~/bin` は忘れません。

たぶん。

---

## GUIを敵視しているわけではありません

GUIは素晴らしいものです。

写真を見るならGUIがいい。
地図を見るならGUIがいい。
絵を描くならGUIがいい。

問題は、

> **同じ操作を正確に何度も繰り返す**

ときです。

人間が毎回、

1. アプリを開く
2. メニューを選ぶ
3. ファイルを選ぶ
4. オプションを設定する
5. ボタンを押す

必要があるなら、それはもしかすると**まだコマンドになっていないだけ**かもしれません。

このリポジトリでは、GUIで発見した有用な操作を、可能ならCLIへ落とします。

GUIは探索に強い。

CLIは再現に強い。

**探索は人間とAIに。再現はプログラムに。**

---

## バグは段差に湧く

このリポジトリの設計思想を一行で表すなら、これかもしれません。

> **バグは段差に湧く。**
> — 山田喜三郎

WindowsからWSLへ。
GUIからCLIへ。
JSONからオブジェクトへ。
人間からAIへ。
AIからスクリプトへ。
部署から部署へ。

境界では、何かが変換されます。

変換されれば、

* 意味が変わる
* 情報が落ちる
* 暗黙の前提が増える
* 「こちらでは動きます」が発生する

だから原則は単純です。

> **段差をなくせ。**
> **なくせない段差は減らせ。**
> **減らせない段差は一箇所に集めろ。**

ちなみに、このREADMEを作るきっかけも段差でした。

ChatGPTとの対話をMarkdownにエクスポートしようとしたところ、ChromeからWSLのLinuxファイルシステムへ直接保存できませんでした。

仕方がないので、

```text
ChatGPT
   |
   v
Chrome
   |
   v
C:\Temp\foobar.md
   |
   v
/mnt/c/Temp/foobar.md
   |
   v
~/tmp/foobar.md
```

と運びました。

そこで作者は言いました。

> 「バグは段差に湧く」

そして続けました。

> [「文科省はWindowsを禁止せよ(笑)」](https://note.com/kisaburo_y/n/n310e49c9483d)

後半については各自でご判断ください。

## なぜホームディレクトリなのか

プロジェクトは終わります。

会社も変わります。

顧客も変わります。

言語も変わります。

フレームワークは、油断していると数年で「legacy」と呼ばれます。

しかし、

```bash
$ cd ~
```

は、かなり長生きします。

ここには「今のプロジェクトの知識」ではなく、

**自分がどう仕事をするか**

を置きます。

プロジェクト固有の成果物と、自分自身の仕事の方法論を分離する。

だからルートは `~` です。

## 設計原則

この環境では、おおむね次の原則を好みます。

1. **小さく作る**
   一つのコマンドには一つの仕事をさせる。

2. **組み合わせる**
   巨大な万能ツールより、小さな部品をパイプやファイルでつなぐ。

3. **繰り返したらスクリプトにする**
   手順書を書く前に、実行可能な手順書を作れないか考える。

4. **AIを部品メーカーにする**
   AIに仕事を丸投げするだけでなく、次回から使えるCLIやスクリプトを作らせる。

5. **推論をキャッシュする**
   一度うまくいった判断は、コード・設定・テスト・文書として固定する。

6. **境界を減らす**
   変換、ラッパー、GUI、独自形式、同期通信をむやみに増やさない。

7. **失敗を資産にする**
   一度踏んだ地雷には看板を立てる。できれば地雷そのものを撤去する。

8. **人間を機械の部品にしない**
   コンピュータができる反復作業を、人間の注意力で実装しない。

## このリポジトリは完成するのか

しません。

これはアプリケーションではなく、**仕事場**だからです。

仕事をして、

面倒なことに遭遇して、

「二度とやりたくない」と思って、

スクリプトを書いて、

AIに直してもらって、

テストして、

`git commit` する。

すると仕事場が少し改善される。

その繰り返しです。

```text
仕事
 ↓
不便
 ↓
抽象化
 ↓
スクリプト
 ↓
再利用
 ↓
もっと難しい仕事
 ↓
新しい不便
 ↓
...
```

これは終わらないループです。

幸い、無限ループとしてはかなり楽しい部類です。

## 最後に

優れた開発環境とは、機能が多い環境ではないと思っています。

**人間が同じことを二度考えなくて済む環境。**

一度得た知識が消えず、
一度解いた問題をもう一度解かず、
昨日の自分が今日の自分を助け、
今日のAIが明日のAIのために道具を残す。

そんな環境が理想です。

IDEとは、コードを書く画面のことではない。

**思考を外部化し、組み合わせ、再利用する場所である。**

そう考えるなら、

```bash
$ pwd
/home/developer
```

ここはもう、IDEです。
